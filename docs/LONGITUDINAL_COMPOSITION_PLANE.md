# C5 implemented contract — longitudinal canonical composition plane

Status: fixture-backed cloud implementation; real longitudinal approval requires L3B.

## Contract and boundary

C5 materializes:

```text
research.eph-longitudinal-composition-plane/v1
```

from one exact parent release of:

```text
research.eph-longitudinal-analysis-frame/v1
```

The grain is exactly one output row per C2 `row_id`. C5 does not reconstruct C2
identity, panel linkage, geography, or raw-source lineage. The output copies the
C2 identity/lineage columns in source order and verifies an exact sequence hash
over:

```text
row_id
household_observation_id
panel_household_id
period
region_id
source_release_id
source_row_identity
```

No income/welfare target and no current individual labor state is a named C5
model feature.

## Named profiles

The versioned registry is
`aligner/codebooks/longitudinal_composition_profiles_v1.json`.
Downstream code must request a named profile rather than inventing a feature
list.

### `P0_LONG`

The compatibility baseline is:

```text
P02  <- CH04
P03  <- CH06
CH07 <- CH07   # governed EPH-only marital-state source concept
P07  <- CH09
P08  <- CH10
P09  <- CH12
P10  <- CH13
P05  <- CH15
IX_TOT <- IX_TOT
```

Where an approved cross-survey semantic concept exists, C5 uses its canonical
name and existing EPH transformation. `CH07` is deliberately different: the
current exact EPH-2024-Q3/CPV-2010 policy does not approve a Census analogue for
it. C5 therefore preserves a bounded EPH-only CH07 domain and **does not invent a
Census mapping**. `P0_LONG` materializes on EPH, but the Census named-profile
hook fails closed for this profile until a source-backed cross-survey decision
exists.

### `P1R_NOLAB_LONG`

This is exactly the currently approved P1-R concept membership minus current
individual labor state:


`CONDACT` is an explicit design exclusion. `H06`, `H11`, and `H16` remain

the reviewed P1-R policy membership and fails if policy evolution would silently
change the basis.

## Reuse of the reviewed compiler

C5 imports the existing EPH-side `_transform_series` implementation from
`aligner.real_semantic_plane`. It does not contain a second table of P02/P03/P05
or housing recodes.

The exact 2024-Q3 + CPV-2010 policy is used in two distinct ways:

1. approved canonical recode definitions are reusable compiler definitions;
2. the exact-pair semantic approval itself is **not** promoted to historical
   longitudinal approval.

The release manifest records both facts. Every C5 row is marked
`reusable_recode_compiled_longitudinal_approval_pending_l3b`.

## Period × concept support inventory

C5 verifies the C2 `schema_inventory.csv`, reconstructs person/household source
support by period, then emits one `support_inventory.csv` row for every
`period × profile concept`.

Each row records:

- raw EPH field and resolved C2 column;
- source role (person/household);
- observed raw and canonical support;
- unexpected codes and impossible canonical values;
- declared special-to-null/special-map handling;
- row/null/non-null counts;
- exact-pair semantic decision and temporal role;
- longitudinal review status;
- cross-survey approval status;
- `longitudinal_approved=false` until L3B.

A raw field absent from a period's C2 source schema fails before materialization.
An unexpected code or impossible transformed value fails immediately. A unioned
C2 column that is blank because the source field was absent cannot masquerade as
support because support is checked against C2's period-specific schema ledger.

## Census compatibility hook

`aligner.census_profile_hook.census_named_profile_frame(...)` projects the same
registry against the canonical columns already generated by the existing real
CPV semantic compiler. It performs no Census recoding itself.

`P1R_NOLAB_LONG` is compatible with the current CPV-2010 compiler. `P0_LONG`
fails closed because CH07 has no approved Census concept.

This proves feature-identity compatibility only; it does not establish temporal
admissibility or statistical transport.

## Release payload and lineage

A release contains:

```text
composition_plane.csv
support_inventory.csv
profile.json
profile_registry.json
semantic_policy.json
parent_manifest.json
qa.json
manifest.json
checksums.sha256
```

The release ID is content-addressed by the exact C2 release/manifest/person
hashes, semantic-policy hash, profile-registry hash and profile ID. Existing
release directories are immutable.

## Commands


```bash

  --c2-release-root /path/to/c2-release \
  --profile P1R_NOLAB_LONG \
  --output-root /path/to/c5-releases
```

Run `P0_LONG` separately when the historical baseline is needed.

## L3B local handoff

C5 cloud verification establishes compiler mechanics only. After the real L2
C2 release exists, L3B must materialize **both** profiles over all 37 periods
(2017-Q1..2026-Q1) and inspect the emitted support inventory.

L3B must fail a concept/profile for an affected period whenever observed source
support cannot be reconciled to source documentation. It must specifically
persist:

- exact C2 parent release ID and manifest/person hashes;
- C5 release IDs and manifest hashes for both profiles;
- 37-period row counts and exact identity-sequence proof;
- every period×concept raw/canonical support;
- all special/null handling and any historical schema/category transition;
- explicit unresolved issues;
- confirmation that `P1R_NOLAB_LONG` exists on every intended L10 model row;
- the exact profile/release identity handed to `encuestador-de-hogares`.

Only that source-backed real-data gate may mark longitudinal concept support as
approved. CPV-2010 donor labor remains the separate C3/L3A handoff.
